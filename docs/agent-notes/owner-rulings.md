# 所有者的裁定与协作习惯

> 相关：`AGENTS.md`「开发模式」（裁定门 → 开工、分支 / 合并口径）、[`git-and-parallel-sessions.md`](git-and-parallel-sessions.md)（合并的具体做法）。

这一份记的是**与所有者协作的方式**，不是技术约定；换 agent 后同样适用（他面对的是「谁在干活」，不是某个工具）。

## 1. 裁定门：给「一个加粗的推荐项 + 备选 + 一句理由」

所有者对轮次拆解里的裁定门（`ROUNDS.md` 各轮「裁定（开工前）」与 § 6）是**整批批**的：
2026-09-15 一句「按推荐项处理」批了 12 项；没有单一推荐项的（Mermaid 三选一、音频、安装器形态、`threads.db` 需实测）他**不碰**，留到对应轮。
2026-09-29 的多 agent 兼容改造也是同一个模式：四项裁定他一次性回「全部按推荐项」。

- **Why**：他不想逐条讨论。**他要的是「有默认值的选择题」，不是开放式问题。**
- **How to apply**：每个裁定项写成「问题 + 一个**加粗的推荐项** + 一句理由 + 备选」；
  一次把该问的都问出来（他喜欢整批处理，不喜欢一步一确认）。
- 裁定后把结果写回对应文档（`docs/design.md` / `AGENTS.md` 的规则 / `rounds/BACKLOG.md`（标 `[x]` + 裁定日期）），
  `ROUNDS.md` 只标「已裁定 按推荐」、不存原文。
- 涉及设计稿的裁定要**真的改 `.dc.html` 并重渲染 PNG**，不能只在文档里写一句（规则 3）。
- **无推荐项、涉及范围或白名单的裁定门，不裁定不开工。**

## 2. 所有方向的合并时机都归他 —— 连「把 main 合进轮次分支」也要先问

R7.5（2026-09-20）收口时 main 新进了「Thread → Session 收敛」（碰组合根 62 行），
我按任务卡「非碰不可的，本分支先合 main」开始**反向合并**，所有者中途说：
「先不要合并到 main 分支，这个修改有毁坏行，由我决定什么时候合并」。
虽然我并没有往 main 合，但为稳妥起见把 main → 轮次分支的合并也撤回了（`git merge --abort`），
解冲突脚本留在 `rounds/round-7.5/merge-main-44d256d.py` 等裁定。

- **Why**：他对合并时机有明确掌控欲（本地 `main` 长期领先 `origin`、多个并行会话各自开分支），
  **任何方向的合并都会改变他手里各分支的关系。**
- **How to apply**：轮次 / 迭代分支上只提交本轮的东西；发现 main 前进并与本轮冲突时，
  先把「冲突面 + 解法（脚本）」写进任务卡并在汇报里问，**不自行合并 —— 哪怕任务卡的前置段写着可以先合**。
  探冲突面用 `git merge-tree --write-tree`（不碰工作树），汇报里给结论 + 双边都改过文件的逐 hunk 对照。
- **例外：他明确说了「合并 / 发版 / 打扫」连成一串时就是授权** —— 例如 2026-09-23 的
  「review 完就发版」整条流水线里，合并 main 由那句指示授权（详见 [`release-pipeline.md`](release-pipeline.md)）。

## 3. 他给的指示要按字面理解，含糊就问他

- 「findings 为 0」是**字面要求**：只有一条不采纳的 P2 时也要再发一轮。
- 口误的版本号（说成「1.4.1」而实际是下一个版本）**要问一句**；
  他给的推荐项里「X 之前」按「新版本之前的全部」理解。
- 「不要用审计来过度设计」（2026-09-23）：审查意见只做最小处理，不借它加机制。
- 「没有代码改动就不要复审啊」（2026-09-23）：合并只动了文档 / 注释时不发复审。
- 「cursor 不可用时中断喊人，不随便回落其他子代理」（2026-09-29）：见 [`review-runbook.md`](review-runbook.md) § 1。

## 4. 他会并行开多个会话 / worktree

这不是偶发情况，是常态（一度同时 8+ 个）。见 [`git-and-parallel-sessions.md`](git-and-parallel-sessions.md)：
提交前重查 status、只 add 自己的路径、commit 后核对文件数与 diff 非空、编号会被抢。
他在活动期间**不要在共享工作副本上开分支**（`git switch -c` 会把他的 commit 带到你的分支上）。
